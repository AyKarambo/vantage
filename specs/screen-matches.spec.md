# Screen spec: Matches (`matches`)

**Source:** `renderer/src/views/matches.ts`, `renderer/src/views/matchDetail.ts`, `renderer/src/components/scoreboard.ts`, `renderer/src/components/roleIcon.ts`, `src/core/matchDetail.ts`, `src/core/playerIndex.ts`, `src/core/analytics/session.ts` (`groupByDay`, `groupBySitting`), `src/core/rankDisplay.ts` (`rankParts`), `renderer/src/prefs.ts` (`MatchColumnsPref`, `matchGrouping`), `src/core/dashboardData.ts` (`selectMatches`, `toMatchRow`, `MATCHES_PAGE_SIZE`, M1; `matchesFilter`, `MatchesTextFilter`, M2), `src/main/dashboard/reads.ts` (`matchesPageRead`, M1/M2).

**Shared context:** Renders from a `DashboardData` snapshot via `ViewContext`; the global filter bar re-scopes the list. The match detail page is a parameterized view (`matchDetail`, opened with `{ matchId }`), registered in the router but outside the sidebar nav list — the sidebar keeps **Matches** highlighted while a detail page is open. Shell-level behaviours that touch this screen (the palette's Match/Map/Hero entries, per-route scroll memory, the Esc/←/→ hotkeys) live in `screen-shell.spec.md`.

## Intent

The match history log with click-through to a full match detail page. Each row opens a dedicated detail view that degrades gracefully across the app's data-capture tiers (live full-roster GEP captures, partial/local-only captures, older legacy records) — a minimal record still renders a complete header even when richer sections have nothing to show.

## List

- Newest-first list of matches in the filtered range. Always visible: result letter (W/L/D, colour-coded), map, map-type pill, clock time (`time()`, locale form e.g. `9:34 PM`; M3 — the day header already carries the date, so a relative age repeated per row under it said nothing a row's own pacing couldn't, and the relative age still lives in the cell's `title` on hover). Every row is clickable (`.match-row.is-clickable`) and navigates to `matchDetail` with that row's `matchId`. There is no per-row game-type label (the app is competitive-only).
- Header count: `"N games in range · newest first · click a match for details"` — or, once the filtered range exceeds the 150-row page cap (`MATCHES_PAGE_SIZE`, `src/core/dashboardData.ts`), `"Showing the 150 most recent of N games in range · …"` (M1) using `DashboardData.matchesTotal` (the true, uncapped filtered count — `matches` itself always caps). A busy range used to show `"150 games in range"` beside a status bar stating the true, larger count right next to it, with no way to reach game #151 from this screen at all.
- **"Show older games" (M1):** appears under the last day/sitting group whenever more of the filtered range remains unloaded (never on a day/flag/map drill-down, whose own scope can't be expressed in the paging IPC call). Fetches the next 150-row page via `bridge.matchesPage({ filters, before: <oldest loaded timestamp>, limit: MATCHES_PAGE_SIZE, text? })` — backed by a pure, unit-tested `selectMatches` (`src/core/dashboardData.ts`, mirrors `playerIndex.ts`'s `selectPlayers`: filter-before → sort newest-first → cap, with `matched` taken from the same sorted array) — and appends the rows into the SAME day-grouped list client-side, without a full dashboard refetch. The extra loaded rows are kept in module state keyed to the current filters, so a role/account/date change (a genuinely different filtered set) drops them, while a background refresh under the same filters (e.g. a new live match landing) leaves them alone.
- **In-list filter row (M2):** result chips (**W / L / D**, multi-select `chip`), map-type chips populated from `ctx.data.byMapType`, and a `.search-input` matching map, hero or account (case-insensitive substring, mirrors `selectPlayers`') — all client-side over what's already loaded, reset the moment you navigate away from Matches (never persisted; the global Role/Season/account controls up top are the only filters that survive navigation). A **"Clear filter"** link appears beside the search box whenever any part of the filter is active. The header subtitle reflects the active filter honestly — `"N of M loaded games match your filter"`, with `"(K total in range)"` appended when more of the range is still unloaded (scoped to the day's or flag's own count instead when a drill-down is active, M3 — see below) — and day/sitting header tallies are computed from the FILTERED rows, so they never disagree with what's actually shown underneath them. The search input's own identity (and caret position) survives a background re-render that would otherwise tear it down mid-typing, the same `hadFocus`/caret-restore idiom `screen-players.spec.md`'s own search box already uses. "Show older games" carries the active filter into its fetch (`matchesFilter`, applied server-side before the page's before/sort/cap) once one is set, so paging in older games while searching returns a full page of ACTUAL matches instead of mostly-discarded unfiltered rows.
- **Day grouping (default) / sitting grouping (S4):** a **"By day / By sitting"** toggle in the view head (hidden during a single-day drill-down — calendar grouping inside one already-picked day would be a distinction with no difference), persisted as the `matchGrouping` pref. By day: rows sit under day headers — "Today" / "Yesterday" for the two most recent calendar days, otherwise a friendly date ("Wed, Jul 2") (pure `groupByDay`). By sitting: rows sit under gap-based sitting headers instead — the same boundary the sidebar's Current-session card and the Overview last-session debrief use (`sessionSettings.gapMinutes`), so a sitting spanning midnight stays one block instead of splitting under two day headers; the open sitting containing "now" reads "Today's session", others read `"Wed · 9:10 PM–1:35 AM"` (pure `groupBySitting`). Both grouping modes show the same shared tally (M3, `DayGroup.draws`/`.srNet`/`.srKnown`): `wins–losses`, extended to `wins–losses–draws` only when the block actually has a draw (a draw used to vanish from the count entirely), plus the block's net SR swing tinted win/loss like a row's own `srDelta` cell — shown only when at least one game in the block logged an `srDelta`, never a fabricated `0%`. The block's winrate rides in the header's `title` instead of a third inline number, and the old `"−1 net"` line that just restated the W–L subtraction is gone.
- **Cross-links inside a row** (`stopPropagation` so the row's detail click stays intact): the map name opens that map's own games here (`{ map }`, see below); each hero name links to that hero's drill-down drawer (`openHeroDrawer`).
- **Row overflow (⋯):** a popover naming the match, offering **Open match** (navigates to `matchDetail`), **Grade on Review** (R4 — only while `MatchRow.reviewed` is false; navigates to `review` with `{ matchId }`, which opens straight to that match's card instead of the newest pending one), **Edit match…** (R4 — `openMatchEditorById`, fetching the `MatchDetail` then opening the same editor the detail page's own Edit button does, so grading/editing never requires opening the row first), and a **Delete match** confirm (see Constraints below).
- **Drill-down scope (`ViewParams.day` / `.flag` / `.map`, H3):** the list can be scoped to one calendar day, one mental flag, or one map — never more than one at a time — with a dismissible `Only <day|flag|map> ✕` chip above the list and an honest "No games match this drill-down" empty state instead of the normal no-games-in-range copy. `day` comes from the Overview activity heatmap and a day header's own click; `flag` from Mental's flag boxes and "What it costs you" links; `map` (H3) from every "open the map" surface app-wide — the Overview scatter dot and its Top-priority callout rows, Focus's map name, the Live "Top priority" card, the Heroes drawer's By-map rows, and the command palette's Map entries — replacing the old behavior of flashing one bar on the Maps ranking, which is now reachable only via a smaller secondary "↗ Maps" link next to Focus's row (the one surface where "how does this map look overall" is still a distinct, useful question from "which games"). All three params are `'route'` in `backStack.ts`'s `PARAM_KINDS`, so Back replays them like any other destination.
  - **Truthful day/flag subtitles, no duplicate day header, day-stepping (M3):** a `day` drill-down states the day's own tally in the header subtitle — `"N games on Wed, Jul 2 · wins–losses[–draws][ · ±SR%]"` (the day-scoped block's own tally, same rules as the day header above) — instead of the generic range copy, which used to just repeat the chip's own date underneath a second, redundant day header; that header is now suppressed for the duration of the drill-down (every other grouping — all days, and every sitting — still shows it). The `Only <day> ✕` chip additionally gets `‹`/`›` buttons stepping to the previous/next day that actually has games, taken from `groupByDay(ctx.data.matches)`'s own keys — not the Overview heatmap's `calendar`, which only spans the last 35 days — so day-stepping is bounded by what's currently loaded and disabled at either end of it; before this the only way to look at the day before was back to Overview, find the heatmap cell, and click again. A `flag` drill-down gets the same truthful-subtitle treatment in place of the generic copy: `"N <flag> games in range"`, e.g. `"46 tilt-flagged games in range"`.
- **Actionable empty state:** an empty range shows "No matches in this range yet." plus a "Show all time (N games)" button (when unfiltered history has games and the range isn't already all-time) and a "Log a match" button opening the quick-log modal.
- **Per-field configurable info ("Customize view").** A "Customize view" affordance lets the user set each of nine fields — **role, heroes, account, SR delta, duration, final score, performance, target grades, flags** — independently to `hidden`, `inline`, or `column` (`MatchColumnMode`/`MatchColumnsPref`, `renderer/src/prefs.ts`):
  - `inline` renders the field as a segment of the row's meta line; `column` renders it as its own vertically aligned column across every row (and then it does **not** also appear inline).
  - Canonical order (inline segments and columns alike): role · heroes · account · SR delta · duration · final score · performance · target grades · flags.
  - Defaults (`MATCH_COLUMNS_DEFAULT`): heroes, account, SR delta = `inline`; role, duration, final score, performance, target grades, flags = `hidden`. A pre-existing stored pref merges any newer keys in as `hidden`.
  - The configuration persists across sessions via renderer prefs (`prefs.get('matchColumns')`).
- **Clean meta line (no placeholders).** The meta line joins only the `inline` segments with a non-empty value, separated by `·` — no `—` placeholder, no leading/trailing/doubled separators; if zero segments are renderable the meta-line element is omitted entirely. A `column`-mode field with no value for a row renders a blank cell so the column stays aligned.
- **Field formatting:** the **role** field renders as a **role icon** (the shared `roleIcon` component — shield/reticle/support-cross/neutral, `currentColor`-tinted). SR delta renders signed and colour-coded (`+25` / `−18`); duration in minutes; final score as recorded (`3–1`). Performance renders as a small mono stat (the 0–100 self-rating) tinted with the winrate ramp; target grades render as compact **Hit / Partial / Missed** pills, one per auto-graded measured target (`'no-stat'` entries skipped); flags render as compact pills per set flag key (Tilt, Toxic, Leaver, +Comms, Abusive). `srDelta` and `finalScore` ride the `MatchRow` contract (`src/shared/contract/dashboard.ts`); `measuredGrades` is passed into `toMatchRow` so list rows carry grades exactly like review-inbox rows.

## Match detail page

`renderer/src/views/matchDetail.ts`, backed by `src/core/matchDetail.ts`; every section renders only when its data exists, so the page degrades tier-by-tier.

- **Header** (always renders): result text (Victory/Defeat/Draw, colour-coded), map name, a meta line (map-type pill · role · account · relative time), mental flag pills when present (Tilt, Toxic mates, Leaver, Positive comms), and a side column with round score (`finalScore`, when captured), duration in minutes (the wall clock, when known), the **played** time to one decimal — labelled *Played*, or *Played (est.)* when it was estimated from the wall clock on a capture without round events (when known) — and hero pills for every hero played (when any).
- **Scoreboard:** renders when the match has roster data or per-hero stats.
  - Full roster (both teams reported): team blocks "Your team" / "Enemy team" separated by a **VS** divider, the tracked player's team first, ordered **5v5** (Tank → DPS → DPS → Support → Support). Each row: a **role icon** (role derived from the hero when the feed omits it), hero, player name ("you" tag on the tracked player's row, tinted), a Perks column (only when at least one entry actually reports perks — GEP does not expose perks today, so it's normally absent, never faked), E / A / D, DMG / HEAL / MIT; the best value in each stat column is highlighted.
  - One team only: the reported team renders normally, followed by a VS divider and "Enemy team not reported by the game feed."
  - No roster but per-hero stats exist: one row per hero played, all tinted as local-only, sub-headed "only your own line was recorded for this match".
  - Neither roster nor per-hero data: the Scoreboard section is absent.
- **Per-hero panel:** rendered when the match has at least one per-hero stat line; a segmented tab control (one tab per hero) appears only when the player used 2+ heroes. Hero-swap segments on the **same hero merge into one chip/row per hero**. Each hero shows its stats **per 10 minutes played** — Elims/10, Assists/10, Deaths/10, DMG/10, HEAL/10, MIT/10, the card subtitled *per 10 minutes played · KDA is a ratio* (with *(est.)* when the played time is estimated) — and **KDA as a ratio** (`(elims + assists) / max(deaths, 1)`). Per-10 rates are dashes when the match's played minutes are unknown.
- **Competitive progress:** rendered only for `Competitive` games, composed through the shared rank renderer (`rankParts`) — the tier/division label, a 🛡 "Rank protected" pill and a buffer hint when the rank is protected, else a within-division progress bar. A per-match SR change (`±N% this match`) is shown when set. The card's note is labelled honestly — **Calculated** (from the rank you set + logged SR), **Reconstructed** (backward from it, may drift), **Estimated from winrate** (C4, a heuristic guess when no rank is set — never drawn with the division bar, the "over the range" delta, or the shield a real reading gets; the tier/division renders in muted text and a **"Set your rank…"** button opens the same Manage-ranks modal Settings uses, navigating there first), **Before reset** (C4, a `pre-reset` match — the same "ladder is discontinuous there" wording `playerHistory.ts` already uses, replacing a raw `pre-reset` pill), or **Reported** (reserved for a future verified GEP rank). There is no "set %" / "Demoted" / re-anchor affordance on the page — "Set your rank…" is the one navigate-only CTA, landing in Settings' own flow rather than duplicating it here.
- **Edit match:** the header carries an **✎ Edit match** action opening the match editor. The game facts (result/role/map/heroes) **and** the manual layer are editable on **every** match — an auto-tracked (GEP) result the feed got wrong (a leaver scored as a loss, a misread draw) can be hand-corrected. Such a correction keeps the record's **⚡ auto** provenance (`source` stays `gep`) and tags it **edited** — a subtle marker in the detail header and on the editor's provenance line; the original feed value is not preserved (no revert), and the game-feed round score/scoreboard are left as-is even when they now contradict the corrected result. The manual layer is mental flags (incl. leaver-team), the per-match SR %, and the active targets' grades. Saves go through `editMatch` (which stamps `factsEditedAt` on a real fact change and now resolves `{ saved: boolean }`, F3) — a demo match (never in real history) reports `saved: false`; the modal closes and refreshes either way, but the toast says "Not saved — "`<map>`" is a demo match…" instead of "Match updated", and skips `gradedThisSession`/the placement-rank-confirm follow-up. On a real save `ctx.refresh()` re-pulls the detail so dependent views update.
- **Grade on Review / Delete match (R4):** beside Edit, the header offers **Grade on Review** — shown only while the match has no saved review (`d.review == null`) — navigating to `review` with `{ matchId }` so the player doesn't have to re-find the game in the inbox, and a **Delete match** confirm (`confirmButton`, same "arm then confirm" two-click as the row menu's own). `deleteMatch` resolves `true` only on an actual delete; only then does the page call `store.goBack()` — a failed or already-gone delete leaves the page in place, since its own toast already explained why.
- **Review's own cross-link (R4):** an expanded Review card's head carries an **"Open match ›"** link into this same detail page, and rides the round score / duration onto its meta line when GEP captured either — the Review card otherwise has nothing but map/hero/result/time to go on.
- **Player History:** always rendered (a hint replaces the table when there's nothing to show). A table of players from this match the tracked player has met in other stored matches — `Player | Prior | Together | As opponents | Last` — derived entirely from locally stored rosters. The count is PRIOR games (this one excluded), which is why it reads one lower than the drill-down it opens; both surfaces say which they show. `Together` and `As opponents` cover only games whose feed reported a team for **both** rows, so they need not add up to `Prior`, and a player with no known relation shows `—` rather than `0W 0L`. Distinguishes "no roster was recorded for this match" from "no players from this match in your tracked history yet". Clicking a name opens that player's page (see `screen-players.spec.md`).
- **Prev/next stepping:** the back row carries the shared `←` **back** control (its destination is wherever you came from, not a fixed screen — see `screen-shell.spec.md`) and a "‹ Older / n / N / Newer ›" stepper through the *filtered* list (disabled at the ends); the shell registers ← / → (older/newer) while a detail page is open, and Esc / Alt+← / the mouse back button for back. `N` reads **`n / 150 loaded`** (M1), not a bare `n / 150`, whenever `DashboardData.matchesTotal` exceeds the loaded `matches.length` — the old bare form implied 150 was the whole filtered range, and a match past the cap couldn't be reached from here at all (Older stops at the edge of what's loaded even though the match plainly exists); once the true total is loaded (e.g. after using Matches' own "Show older games"), the suffix drops and it reads a plain `n / N`.

## Out-of-Scope

- **Share URL** — publishing matches to a shareable web link is out of scope (it would add a second outbound path beyond Notion, violating guardrail #5). No Share/publish affordance appears anywhere.
- **End-of-match screenshots** — there is no screenshot capture, storage, or gallery. The feature was removed; the detail page has no screenshots section.
- Column sorting on the list (not present — the list is always newest-first). Pagination is now partly in-scope (M1) — "Show older games" reaches past the 150-row cap — but there is still no jump-to-page or numbered-page affordance, only "load the next 150 older" from the bottom of the list. Result/map-type/search filtering is now in-scope too (M2, see the in-list filter row above); still absent: persisting the in-list filter across navigation (by design — it resets), and filtering by anything beyond result/map-type/map-hero-account text (no date/role/SR-delta/flag filtering in this row — the global filter bar and the `day`/`flag`/`map` drill-downs already cover those).

## Constraints & edge cases

- **Guardrail #1 (account safety):** all detail-page data comes solely from Overwolf GEP or manual logging. Fields the GEP does not expose (perks, live rank) are optional/best-effort and simply absent — never memory-read, injected, or fabricated. The scoreboard may only show information visible on the in-game end-of-match screen.
- Live GEP matches persist the **full reported roster** (when provided) and the round score onto the stored `GameRecord`; other players' names/records are local-only and never sent to Notion (the exporter excludes rosters and review data).
- Player History is derived at query time from stored rosters across all history — no separate store.
- All stored data stays local-first (guardrail #5).
